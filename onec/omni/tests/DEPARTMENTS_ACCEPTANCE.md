# Распределение MAX по отделениям — приемка

Версия для тестирования: 1.1.0.35.

Статус: эффективная изоляция контактов, истории и состояний проверена в локальной
тестовой УМЦ через отдельные COM-сеансы двух операторов, пользователя без отделения
и пользователя с Полными правами. Полная матрица ниже в клиентской конфигурации
ещё НЕ выполнена. CFE из тестовой сборки не является разрешением обновлять рабочую базу.
Актуальный протокол: [ACCEPTANCE-1.1.0.35.md](../../../install-guide/ACCEPTANCE-1.1.0.35.md).

## Настройка тестового контура

1. Отключить внешние обмены и использовать только отдельного тестового бота/VDS.
2. Под Полными правами создать «Взрослое» и «Детское» в справочнике «Отделения MAX».
   «Недоступно для выбора» скрывает отделение от новых обращений, но не скрывает
   уже закрепленную переписку.
3. В непериодическом регистре «Отделения пользователей MAX» назначить каждому
   оператору одно отделение. Периодов/истории назначения нет. После изменения
   назначения необходимо перезапустить сеанс (параметры RLS кешируются).
4. Назначить роль «МАКС: оператор отделения» операторам, сохранив требуемые штатные
   права на пациентов. Не выдавать им Полные права. Проверить суммарные права:
   другая роль с неограниченным чтением может перекрыть RLS. Основная роль
   расширения не используется кодом как признак административного доступа.
5. Отдельно проверить права фонового пользователя на все отделения. Он должен
   обрабатывать и новые контакты без отделения. Не запускать два потребителя
   одного продуктивного бота.
6. Загрузить MAX_WELCOME и прочие используемые стандартные шаблоны. Два отделения
   не создаются автоматически; данные рабочей базы не мигрируют без согласования.

## Обязательные сценарии

- Новый MAX-контакт передает свой подписанный телефон, выбирает отделение.
  Проверить найденного, не найденного и неоднозначно найденного пациента.
- Подпись/чужой телефон отклонены: выбор отделения не применяется.
- До выбора контакт видят только Полные права; без назначения оператор не видит
  ни одного диалога. Старые диалоги без отделения остаются у Полных прав.
- Два оператора видят только свое отделение. Полные права видят оба.
- Один пациент, два контакта одного бота в разных отделениях: разные строки,
  переписки, непрочитанные и состояния; «Закрыть» не закрывает соседний диалог.
- Подмена контакта, бота, пациента или ключа при открытии, поиске пациента,
  отправке и переносе заявки не открывает чужой диалог.
- Проверить стандартные списки контактов, истории, состояний и очереди, не только
  форму Единого чата. Проверить итоговые права каждой реально используемой роли.
- Повторная доставка callback и одновременное нажатие разных отделений:
  сохраняется первый выбор и ровно одна отбивка в истории. Сбой ответа VDS
  после фиксации выбора не откатывает назначение.
- Кнопка с неизвестным/удаленным/отключенным отделением отклоняется; повторный
  «Начать» предлагает актуальные отделения, если отделение еще не выбрано.
- Отправка оператором, приветствие, очередь уведомлений о записи и callback
  подтверждения/отмены работают с новой моделью прав.
- Обычная запись заявки оператором не падает из-за RLS контакта в другом отделении
  или без отделения. Автоматическое обновление очереди по событию объекта идет
  отдельным служебным серверным путем, без возвращения данных оператору.

## Принятые границы

Первый выбор отделения закрепляется за контактом; старой кнопкой его не изменить.
Самообслуживание по смене отделения и перенос старых диалогов не реализованы.
История старых состояний с пустым отделением сохраняется; после выбора отделения
новый статус ведется отдельно. Административное исправление назначения пользователя
не заменяет миграцию переписки.

Клавиатура делится на сообщения по 30 рядов, по одной кнопке в ряду, согласно
[документации MAX](https://dev.max.ru/docs/chatbots/bots-coding/library/js).
Служебный request_contact остается разрешенным.

Статические проверки:

- 13 проверок исходных контрактов проходят.
- Изолированная загрузка XML, /CheckConfig расширения и сборка CFE проходят
  на платформе 8.3.27.2214. Это не проверка применимости к клиентской базе.
- Валидаторы ролей и форм проходят. Объектный XML-валидатор сообщает об
  отсутствии v8:Type у пользователя/ответственного: здесь используется v8:TypeId
  c7e82c12-7586-469b-a703-fd2a4161dac9, как в существующей истории и состояниях.
  Платформа этот формат принимает. Соответствие типу пользователей клиента
  проверяется при применении на тестовом контуре.
- BSL lint интеграции не выявил ошибок; в прежней форме остаются замечания к
  ПолучитьФорму и конструкторам шрифта. Они не являются результатом проверки
  исполняемого клиентского интерфейса.

```powershell
python -m unittest discover -s onec/omni/tests -p test_departments_source.py -v
```

Они проверяют исходные контракты, а не исполнение BSL, эффективные права или доставку.
