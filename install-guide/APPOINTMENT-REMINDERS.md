# Напоминания и кнопки записи: расширение 1.1.0.30 / backend 1.0.6

Начиная с расширения **1.1.0.29** сроки при записи объекта задаются в табличной части
[Даты события](EVENT-DATES.md): до/после выбранной даты, сама дата или ручной
алгоритм. Сообщения формируются при записи, отправляются отдельным заданием очереди.

## Что изменено

- В 1.1.0.30 стандартный набор содержит три рассылки: уведомление о создании без кнопок, просьбы подтвердить за 24 и за 2 часа. Команда «Создать и включить уведомление о новой записи» больше не создаёт немедленный запрос подтверждения и его шаблон `MAX_APPOINTMENT_CONFIRM_REQUEST`. Удалённые пользователем записи не восстанавливаются этими командами. Существующие старые записи других баз автоматически не удаляются и не отключаются: их нужно проверить отдельно.
- Убрана заимствованная картинка `КрасныйКруг` и ссылки на неё в форме календаря. Автообновление чата обозначается текстом «Онлайн»/«Офлайн» без цветных кругов.
- Кнопки шаблона редактируются таблицей значений на форме: ряд, действие, текст, параметр, URL. Хранение — прежний реквизит `КнопкиMAX` с JSON; табличная часть справочника не добавляется.
- Действия «Подтвердить приём» и «Отменить приём» формируют callback, не открывают миниприложение. Сложный или нераспознанный JSON остаётся доступен в расширенном режиме и не перезаписывается молча.
- Два отдельных стандартных шаблона: `MAX_APPOINTMENT_REMINDER_24H` и `MAX_APPOINTMENT_REMINDER_2H`.
- MAX передаёт нажатие на VDS. 1С получает его при очередном опросе и сама изменяет заявку, затем VDS обновляет сообщение MAX, убирая кнопки. Входящего подключения VDS к 1С нет.
- Проверяются контакт MAX, бот, пациент заявки, состояние, будущее время приёма и дата/время начала из кнопки. Старые кнопки после переноса не применяются. Повтор подтверждения/отмены не записывает документ повторно.
- Входящие события подтверждаются ACK после обработки. Незавершённые события выдаются повторно через две минуты. Это не обещание exactly-once; повторные изменения заявки защищены идемпотентной обработкой.

## Порядок обновления

1. Сохранить резервную копию базы 1С, текущий CFE и данные Redis. Не удалять Redis volume. На время обновления остановить именно обмен MAX, не включать заблокированные задания других обменов.
2. Обновить backend на VDS по [инструкции Debian/Docker](DEBIAN-DOCKER.md). Для уже настроенного стенда: `git pull --ff-only`, затем `docker compose up -d --build backend`. Сверить имя сервиса со своим compose-файлом. Секреты и URL сохраняются прежними.
3. Проверить `/healthz` и `/api/v1/version`. С сервисным ключом запрос `/api/v1/onec/capabilities` должен вернуть `incoming_ack: true` и `callback_answer: true`. Ключ не передавать в URL и не публиковать в журналах/скриншотах.
4. Обновить расширение существующей записью `бит_МедицинаМАКС` из [CFE](../onec/omni/BUILD/бит_МедицинаМАКС_2026_09_09.cfe). Перезапустить сеансы, проверить версию 1.1.0.30. Новое расширение не забирает очередь у старого backend, если проверка возможностей не пройдена.
5. Проверить настройку базы **«Признак подтверждённой заявки»**: поддерживается состояние заявки либо свойство со значением Истина. Без настройки подтверждение отклоняется; отмена от неё не зависит. Пользователь задания должен иметь штатные права на изменение заявок и свойства подтверждения. Типовые проверки записи не отключаются.
6. Открыть сохранённую карточку активного MAX-бота. Команда **«Создать и включить напоминания за сутки и 2 часа»** создаёт недостающие стандартные шаблоны/рассылки и активирует их для этого бота. Эта команда разрешает реальные отправки при запуске нового задания очереди; выполнять её после теста на отдельном боте/контуре. Сама установка CFE ничего не активирует.
7. Для немедленного уведомления выполнить «Создать и включить уведомление о новой записи». Проверить активный набор: ровно три указанные рассылки. Старый отдельный «MAX: запрос подтверждения записи», если он остался в базе, отключить; его шаблон больше не поставляется. В используемых пользовательских шаблонах заменить старые `open_app` на действия «Подтвердить приём»/«Отменить приём». Уже отправленные сообщения и подготовленные снимки очереди не мигрируют; перед запуском отправки проверить старую очередь.
8. В рабочем контуре отдельно настроить новое задание отправки очереди MAX с интервалом не более минуты. Входящий обмен не отправляет очередь. Часовой пояс сеанса задания должен совпадать с журналом записи. В копии с глобально заблокированными заданиями запускать новое задание очереди вручную, не снимать общую блокировку: автоматической своевременной отправки там не будет.

## Очередь и диагностика

Рассылки за24/2 часа формируются при записи заявки, а не поиском заявок
по временным окнам. Получатели и текст сохраняются сразу. Перенос и отмена
пересчитывают ожидающие сообщения при записи. Подробнее о дедупликации,
неизвестном исходе доставки, просроченных сообщениях и миграции:
[Событийная очередь](EVENT-DATES.md).

Новый регистр: `бит_омни_ОчередьСообщенийMAX`, журнал: `МАКС.Очередь.*`.
Старый `бит_омни_ДоставкаНапоминанийMAX` остается только для истории.
Установка не включает новое задание и не перебирает существующие заявки.

Входящие события: `ОМНИ.MAX.VDS.Polling`, `ОМНИ.MAX.VDS.Processing`,
`ОМНИ.MAX.Callback.Answer`. Если заявка изменена, но обновление сообщения
MAX не принято, изменение не откатывается — остается запись в журнале.
Сохранность входящей Redis-очереди требует сохранного volume/AOF.

## Проверка перед включением клиенту

На отдельном тестовом боте проверить: оба срока; подтверждение; отмену; повтор нажатия; кнопку после переноса; несовпадение пациента; недоступность VDS; повтор входящего события после истечения lease. Сравнить состояние заявки, журнал, историю MAX и регистр доставки. Модульные тесты и сборка CFE не заменяют этот сквозной тест на клиентской конфигурации.

Фикстуры в `onec/omni/tests` выполняются только в изолированной тестовой базе: `template-buttons-regression.bsl`, `appointment-payload-regression.bsl`, `appointment-callback-regression.bsl`, `reminder-activation-regression.bsl`, `queue-onwrite-regression.bsl`, `queue-state-regression.bsl`, `queue-transport-regression.bsl`. Порядок запуска и очистки фикстур — в README тестов; HTTP в этих тестах отсутствует.

Исторические проверки выпуска1.1.0.27: сборка CFE платформой 8.3.27.2214; перечисленные фикстуры в локальной УМЦ 2.0.49.91; подтверждение через настроенное состояние заявки; 17 backend-тестов; отдельный интеграционный тест claim/ACK на Redis 7. Групповой кейс пропускается в 2.0 без этого реквизита, в 2.1 используется проверка наличия метаданных. Сквозная доставка через настоящий MAX и клиентская база 2.1 в эту проверку не входили.
