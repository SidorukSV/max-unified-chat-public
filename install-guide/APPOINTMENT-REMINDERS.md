# Напоминания и кнопки записи: расширение 1.1.0.27 / backend 1.0.6

## Что изменено

- Кнопки шаблона редактируются таблицей значений на форме: ряд, действие, текст, параметр, URL. Хранение — прежний реквизит `КнопкиMAX` с JSON; табличная часть справочника не добавляется.
- Действия «Подтвердить приём» и «Отменить приём» формируют callback, не открывают миниприложение. Сложный или нераспознанный JSON остаётся доступен в расширенном режиме и не перезаписывается молча.
- Два отдельных стандартных шаблона: `MAX_APPOINTMENT_REMINDER_24H` и `MAX_APPOINTMENT_REMINDER_2H`.
- MAX передаёт нажатие на VDS. 1С получает его при очередном опросе и сама изменяет заявку, затем VDS обновляет сообщение MAX, убирая кнопки. Входящего подключения VDS к 1С нет.
- Проверяются контакт MAX, бот, пациент заявки, состояние, будущее время приёма и дата/время начала из кнопки. Старые кнопки после переноса не применяются. Повтор подтверждения/отмены не записывает документ повторно.
- Входящие события подтверждаются ACK после обработки. Незавершённые события выдаются повторно через две минуты. Это не обещание exactly-once; повторные изменения заявки защищены идемпотентной обработкой.

## Порядок обновления

1. Сохранить резервную копию базы 1С, текущий CFE и данные Redis. Не удалять Redis volume. На время обновления остановить именно обмен MAX, не включать заблокированные задания других обменов.
2. Обновить backend на VDS по [инструкции Debian/Docker](DEBIAN-DOCKER.md). Для уже настроенного стенда: `git pull --ff-only`, затем `docker compose up -d --build backend`. Сверить имя сервиса со своим compose-файлом. Секреты и URL сохраняются прежними.
3. Проверить `/healthz` и `/api/v1/version`. С сервисным ключом запрос `/api/v1/onec/capabilities` должен вернуть `incoming_ack: true` и `callback_answer: true`. Ключ не передавать в URL и не публиковать в журналах/скриншотах.
4. Обновить расширение существующей записью `бит_МедицинаМАКС` из [CFE](../onec/omni/BUILD/бит_МедицинаМАКС_2026_09_08.cfe). Перезапустить сеансы, проверить версию 1.1.0.27. Новое расширение не забирает очередь у старого backend, если проверка возможностей не пройдена.
5. Проверить настройку базы **«Признак подтверждённой заявки»**: поддерживается состояние заявки либо свойство со значением Истина. Без настройки подтверждение отклоняется; отмена от неё не зависит. Пользователь задания должен иметь штатные права на изменение заявок и свойства подтверждения. Типовые проверки записи не отключаются.
6. Открыть сохранённую карточку активного MAX-бота. Команда **«Создать и включить напоминания за сутки и 2 часа»** создаёт недостающие стандартные шаблоны/рассылки и активирует их для этого бота. Эта команда разрешает реальные отправки при следующем запуске обмена; выполнять её после теста на отдельном боте/контуре. Сама установка CFE ничего не активирует.
7. Для старых шаблонов запроса подтверждения заменить строки кнопок действиями «Подтвердить приём»/«Отменить приём» и сохранить. Либо явно перезагрузить нужные стандартные шаблоны, предварительно сохранив свои тексты: перезагрузка заменяет пользовательские настройки выбранного шаблона. Уже отправленные старые сообщения не мигрируют.
8. В рабочем контуре настроить запуск существующего задания обмена MAX с интервалом не более минуты. Часовой пояс сеанса задания должен совпадать с журналом записи. В копии с глобально заблокированными заданиями запускать обмен вручную, не снимать общую блокировку: автоматической своевременной отправки там не будет.

## Временные окна и диагностика

Отбор выполняется за 24 часа и за 2 часа с допуском 15 минут после соответствующего порога. Пропущенные окна не догоняются: например, сообщение «за сутки» не уйдёт за три часа до приёма. За один вызов обрабатывается до 100 кандидатов каждого этапа.

Отправляются только рабочие индивидуальные заявки до прихода пациента: без пометки удаления, с действующим связанным контактом MAX. Заблокированные контакты, групповые/отменённые заявки исключены. Подтверждённая рабочая заявка также может получить второй этап напоминания.

Регистр `бит_омни_ДоставкаНапоминанийMAX` хранит ключ бот + заявка + дата начала + этап и итог отправки. При таймауте без подтверждённого MID или аварии процесса состояние становится неопределённым; автоматический повтор отключён, чтобы не дублировать уже доставленное сообщение. Требуется ручная сверка с MAX. Не удалять записи регистра для «повтора» без этой сверки.

События журнала: `ОМНИ.MAX.VDS.Polling`, `ОМНИ.MAX.VDS.Processing`, `ОМНИ.MAX.Callback.Answer`, `МАКС.Напоминания.*`. Если изменение заявки выполнено, но MAX не принял обновление сообщения, изменение не откатывается; об этом остаётся запись в журнале. Неподтверждённые сообщения Redis сохраняются при перезапуске при условии сохранного volume/AOF.

## Проверка перед включением клиенту

На отдельном тестовом боте проверить: оба срока; подтверждение; отмену; повтор нажатия; кнопку после переноса; несовпадение пациента; недоступность VDS; повтор входящего события после истечения lease. Сравнить состояние заявки, журнал, историю MAX и регистр доставки. Модульные тесты и сборка CFE не заменяют этот сквозной тест на клиентской конфигурации.

Фикстуры в `onec/omni/tests` выполняются только в изолированной тестовой базе: `template-buttons-regression.bsl`, `appointment-payload-regression.bsl`, `appointment-callback-regression.bsl`, `reminder-activation-regression.bsl`, `reminders-regression.ps1`, `reminder-response-regression.ps1`. Скрипты PS1 выдают BSL как JSON-строку для `execute_code`, сами к базе не подключаются. Проверки записей используют откат транзакции; HTTP в них отсутствует.

Проверено при подготовке версии: сборка CFE платформой 8.3.27.2214; перечисленные фикстуры в локальной УМЦ 2.0.49.91; подтверждение через настроенное состояние заявки; 17 backend-тестов; отдельный интеграционный тест claim/ACK на Redis 7. Групповой кейс пропускается в 2.0 без этого реквизита, в 2.1 используется проверка наличия метаданных. Сквозная доставка через настоящий MAX и клиентская база 2.1 в эту проверку не входили.
