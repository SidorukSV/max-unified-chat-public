# API обмена 1С ↔ VDS

Backend работает как публичный шлюз между MAX и 1С:

1. MAX отправляет webhook на VDS.
2. Backend проверяет секрет webhook и кладёт событие в Redis-очередь.
3. 1С регламентным заданием забирает входящие сообщения из backend.
4. 1С отправляет исходящие сообщения в backend.
5. Backend вызывает MAX Bot API `POST /messages`.

## Авторизация 1С

Все методы `/api/v1/onec/*` требуют сервисный ключ.

Можно передать ключ одним из способов:

```http
X-Onec-Api-Key: <ONEC_API_KEY>
```

или:

```http
Authorization: Bearer <ONEC_API_KEY>
```

Секрет задаётся в `backend/.env.production`:

```env
ONEC_API_KEY=replace_with_strong_random_service_key
```

## Входящие сообщения MAX для 1С

### `GET /api/v1/onec/capabilities`

Немутирующая проверка совместимости с тем же сервисным ключом. Ответ:

```json
{"incoming_ack":true,"callback_answer":true}
```

Перед первым запросом входящих событий новое расширение обязано проверить
`incoming_ack=true` и `callback_answer=true`. Если метод отсутствует (`404`),
не авторизован (`401`) или возможностей нет, опрос очереди не выполняется:
сначала нужно обновить backend. Это предотвращает потерю событий на старом
backend, который может проигнорировать неизвестный query-параметр `ack=true`
и удалить событие при выдаче. Проверка capabilities не читает и не меняет очередь.

### `GET /api/v1/onec/messages/incoming`

1С вызывает метод по расписанию и забирает пачку входящих событий.

Параметры:

- `limit` — максимальное количество сообщений за один вызов. По умолчанию `ONEC_POLL_DEFAULT_LIMIT`, верхняя граница `ONEC_POLL_MAX_LIMIT`.
- `waitMs` — опциональное ожидание long polling при пустой очереди, в миллисекундах. Верхняя граница backend — `55000`.
- `ack=true` — надёжная выдача с арендой события и отдельным подтверждением обработки.
  Без параметра (или с `ack=false`) сохраняется старый режим удаления при выдаче
  для совместимости с ранее установленными расширениями. Другие значения — ошибка `400`.

Пример:

```bash
curl "https://chat.example.com/api/v1/onec/messages/incoming?limit=50&waitMs=25000" \
  -H "X-Onec-Api-Key: ${ONEC_API_KEY}"
```

Ответ:

```json
{
  "messages": [
    {
      "id": "9aebd640-c52a-4f3d-a216-b9b6c5efb928",
      "received_at": "2026-09-03T13:00:00.000Z",
      "source": "max_webhook",
      "update_type": "message_created",
      "update": {
        "update_type": "message_created"
      }
    }
  ],
  "remaining": 0
}
```

`update` содержит исходный объект `Update` от MAX без изменений.

### Выдача с подтверждением обработки

Новое расширение должно всегда запрашивать `ack=true`. В этом режиме событие
атомарно переносится из очереди в хранилище неподтверждённых событий Redis и не
удаляется после HTTP-ответа. Каждому событию добавляются:

```json
{
  "receipt": "opaque-unique-delivery-receipt",
  "lease_expires_at": 1788865320000
}
```

Внешний объект ответа дополнительно содержит `lease_ms: 120000`.
`lease_expires_at` — время окончания аренды в миллисекундах Unix по часам Redis.
`remaining` учитывает только готовую очередь, не события в обработке.

### `POST /api/v1/onec/messages/incoming/ack`

После успешной фиксации бизнес-операции в базе 1С вызывает метод с сервисным ключом:

```json
{"receipts":["opaque-unique-delivery-receipt"]}
```

Ответ: `{"ok":true,"acknowledged":1}`. Максимум квитанций в одном запросе —
`ONEC_POLL_MAX_LIMIT`. Пустой/некорректный массив даёт `400`. Подтверждается только
ещё действующая квитанция конкретной выдачи, не `id` события. Неизвестная,
просроченная или уже подтверждённая квитанция не удаляет данные и не увеличивает
`acknowledged`.

При ошибке обработки, обрыве соединения или падении 1С ACK не отправляется.
Следующий опрос с `ack=true` после окончания аренды возвращает то же событие с тем
же `id` и новой `receipt`. Возврат просроченных событий, выдача и ACK реализованы
атомарными Lua-операциями Redis. Старую квитанцию нельзя использовать для удаления
повторно выданного события. Автоматическое восстановление не требует отдельного
worker или входящего подключения к 1С.

Это доставка **как минимум один раз**, а не «ровно один раз»: 1С обязана проверять
повтор события и не выполнять повторно подтверждение/отмену. Фиксация результата
в 1С предшествует ACK. Если ответ на ACK потерян, повторная обработка события
должна оставаться безопасной. ACK после записи результата не следует ставить в
зависимость от успешной отправки пользовательского уведомления в MAX.

Обрабатывать и подтверждать события лучше по одному (`limit=1`), чтобы длительная
пачка не пережила двухминутную аренду. Не запускайте одновременно старые потребители
без ACK и новое расширение: старый потребитель всё ещё может забрать готовое событие
без гарантии повтора. Некорректные сохранённые JSON-конверты атомарно перемещаются
в очередь `REDIS_INCOMING_DEAD_LETTER_QUEUE_KEY`, а не теряются. Корректные конверты
с неподдерживаемыми бизнес-событиями 1С должна явно обработать/отклонить и подтвердить.

Служебные ключи Redis: `<REDIS_INCOMING_QUEUE_KEY>:inflight` (hash) и
`<REDIS_INCOMING_QUEUE_KEY>:leases` (sorted set). Для сохранности при перезапусках
Redis нужен постоянный том и AOF (в поставляемом Compose включены). Это не заменяет
резервное копирование и не исключает окно потери данных при аварии носителя или
питания согласно настройке `appendfsync`. В журналах операций выдачи/ACK записываются
только количества и режим, без текста переписки, payload, квитанций и секретов.

## Настройки расширения 1С

В расширении добавлены настройки раздела `MAX.VDS`:

- `MAX_VDS_URL` — публичный HTTPS-адрес backend/VDS без завершающего `/`, например `https://chat.example.com`;
- `MAX_VDS_API_KEY` — сервисный ключ для заголовка `X-Onec-Api-Key`;
- `MAX_VDS_POLL_LIMIT` — размер пачки входящих сообщений за один опрос, по умолчанию `50`;
- `MAX_VDS_LONG_POLL_WAIT_MS` — время удержания запроса backend при пустой очереди, по умолчанию `25000`.

Регламентное задание расширения:

- имя: `бит_омни_ОбменСообщениямиMAXЧерезVDS`;
- метод: `бит_омни_ИнтеграцияСMAX.ВыполнитьРегламентныйОбменСVDS`;
- расписание по умолчанию: каждые 60 секунд;
- при заполненных `MAX_VDS_URL` и `MAX_VDS_API_KEY` забирает входящие события из очереди VDS и обрабатывает их штатным обработчиком MAX-чата;
- исходящие сообщения 1С при включенном VDS-обмене отправляются через `/api/v1/onec/messages/outgoing`, а не напрямую в MAX API.

## Исходящие сообщения из 1С в MAX

### `POST /api/v1/onec/messages/outgoing`

1С передаёт одно сообщение или пачку сообщений. Backend отправляет их в MAX Bot API `POST /messages`.

Одинарный payload:

```json
{
  "client_message_id": "onec-message-0001",
  "user_id": 123456789,
  "text": "Здравствуйте",
  "notify": true
}
```

Пачка:

```json
{
  "messages": [
    {
      "client_message_id": "onec-message-0001",
      "user_id": 123456789,
      "text": "Здравствуйте"
    },
    {
      "client_message_id": "onec-message-0002",
      "chat_id": 987654321,
      "text": "Сообщение в чат"
    }
  ]
}
```

Поддерживаемые поля адресации:

- `user_id` / `userId`;
- `chat_id` / `chatId`.

Поддерживаемые поля тела сообщения:

- `text`;
- `attachments`;
- `link`;
- `notify`;
- `format`.

Дополнительный query-параметр MAX:

- `disable_link_preview` / `disableLinkPreview`.

Пример:

```bash
curl -X POST "https://chat.example.com/api/v1/onec/messages/outgoing" \
  -H "X-Onec-Api-Key: ${ONEC_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "client_message_id": "onec-message-0001",
    "user_id": 123456789,
    "text": "Здравствуйте"
  }'
```

Успешный ответ:

```json
{
  "ok": true,
  "sent": 1,
  "failed": 0,
  "results": [
    {
      "ok": true,
      "client_message_id": "onec-message-0001",
      "max_response": {
        "message": {}
      }
    }
  ]
}
```

Если часть сообщений не отправилась, backend возвращает HTTP `207` и детальный список результатов.

## Ответ на нажатие кнопки

Событие `message_callback` проходит ту же очередь, что и сообщения: MAX → webhook
VDS → Redis → исходящий запрос long polling из 1С. Backend не подключается к базе
1С и не принимает бизнес-решение о подтверждении или отмене приёма. В `update`
сохраняются исходные `callback.callback_id`, `callback.user.user_id`,
`callback.payload` и `message`. Проверка отправителя, допустимости действия и
повторных нажатий выполняется в 1С до изменения записи на приём.

### `POST /api/v1/onec/callbacks/answer`

После обработки 1С передаёт ответ для MAX через тот же сервисный ключ:

```json
{
  "callback_id": "callback-id-from-update",
  "message": {
    "text": "Приём подтверждён",
    "attachments": [],
    "notify": false
  },
  "disable_link_preview": true
}
```

`callback_id` — обязательная непустая строка. `message` — обновлённое исходное
сообщение, содержащее `text`, `attachments` и/или `link`; также поддерживаются
`notify` и `format`. Пустой массив `attachments` позволяет убрать кнопки из
обновляемого сообщения. Устаревшее поле `notification` не передаётся.

Backend выполняет `POST /answers?callback_id=...` в MAX с токеном бота в заголовке
`Authorization`. Адрес назначения фиксирован настройкой MAX API; переданные
`url`, `user_id` и неизвестные поля не используются.

Успех: HTTP `200`, `{"ok":true,"max_response":{"success":true}}`.
Ошибки: `400` — некорректный payload, `401` — сервисный ключ, `502` — сбой MAX
или ответ `success:false`. Неуспешное обновление сообщения в MAX само по себе не
означает, что нужно повторно менять состояние записи в 1С: бизнес-операция должна
оставаться идемпотентной. Транспорт не выполняет автоматических повторов.

Контракт MAX: [официальное описание POST /answers](https://dev.max.ru/docs-api/methods/POST/answers).

## Webhook MAX

### `POST /api/v1/max/webhook`

Публичный endpoint для Webhook-подписки MAX.

Backend:

- проверяет заголовок `X-Max-Bot-Api-Secret`, если задан `MAX_WEBHOOK_SECRET`;
- проверяет, что тело запроса — JSON-объект;
- кладёт объект `Update` в Redis-очередь;
- возвращает MAX `200 OK`, если событие принято в очередь.

Пример URL:

```text
https://chat.example.com/api/v1/max/webhook
```

Ответ:

```json
{
  "ok": true,
  "queued": true,
  "message_id": "9aebd640-c52a-4f3d-a216-b9b6c5efb928"
}
```

## MAX Bot API

Для отправки сообщений backend использует официальный endpoint MAX Bot API:

- `POST https://platform-api2.max.ru/messages`
- авторизация через заголовок `Authorization: <MAX_BOT_TOKEN>`

Практическое ограничение MAX: не более двух сообщений в секунду в один диалог/чат. Если на стороне 1С возможны массовые отправки в один и тот же диалог, нужно дозировать пачки либо добавить отдельный worker с rate-limit.
